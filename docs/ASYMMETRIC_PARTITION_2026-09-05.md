# 비대칭 DB 단절과 이전 워커의 늦은 결과

2026-09-05. 이전 워커만 DB에서 고립된 동안 새 워커가 작업을 회수하고 완료한 뒤, 이전 워커의 성공 또는 오류가 도착해도 최신 데이터를 변경하지 못하는지 검증했다. 운영 코드 수정 없이 기존 lease 검사·취소·소유권 조건으로 두 사례 모두 통과했다.

## 재현 방법

워커 3개에 각각 독립 Prisma 연결 풀을 사용한다. 이전 워커의 DB proxy와 정상 워커 2개의 DB proxy를 분리한다. 관측용 연결은 DB에 직접 연결한다.

1. 이전 워커가 첫 시도를 시작하고 합성 HTTP/2 서버의 실제 SDK embedding 응답을 받은 뒤, 서비스 경계에서 반환을 보류한다.
2. 이전 워커의 DB 소켓만 끊고 신규 연결을 차단한다. 정상 워커들이 drain해도 아직 유효한 lease를 회수하지 않는지 확인한다.
3. 테스트 lease 1.2초가 실제로 만료될 때까지 기다린다. 이전 워커의 heartbeat 실패로 signal이 KnowledgeIndexLeaseLostError와 함께 취소됐는지도 확인한다.
4. 원문을 다른 내용으로 바꿔 정상 워커 2개가 동시에 회수를 시도한다. 같은 job이 attempt 2로 완료되고 최신 내용·1024차원 embedding·새 provenance를 저장한다.
5. 이전 워커의 DB 연결을 복구한 다음 보류한 응답을 반환한다. 성공 반환과 오류 발생을 각각 실행한다.
6. 최신 청크 전체, 파일 전체(상태·오류·시각·metadata 포함), 작업 전체가 이전 결과 도착 전 snapshot과 정확히 같은지 검사한다. 총 embedding 호출은 2회다.

성공 사례는 오래된 내용으로 인덱스를 교체하지 못하는지 확인한다. 오류 사례는 이전 시도의 실패 처리 경로가 최신 파일 상태나 오류 메시지를 변경하지 못하는지 확인한다.

## 검증 결과

- `npm run test:network-e2e`: 15/15 PASS, 23.413초. 임시 DB `queue_e2e_4536110db77d452b8ed94db3715a115b` 삭제 완료.
- `npm run test:queue-http-e2e`: 7 suites / 39개 PASS, 47.724초. 임시 DB `queue_e2e_456949e428d64937a73220c951725c0d` 삭제 완료.
- `npm run verify`: build/typecheck/lint, 서버 단위 197개·데모 37개 PASS. 최초 린트에서 보조 함수 bind의 타입 추론 오류를 발견해 명시적 함수 타입을 추가한 뒤 전체 verify를 다시 통과했다.

## 범위와 남은 작업

DB 단절과 lease 회수는 실제 소켓·PostgreSQL을 사용한다. 늦은 응답은 SDK 역직렬화 이후 서비스 경계에서 보류하므로, 실제 AWS가 취소 후 응답을 전달하는 동작을 재현했다고 주장하지 않는다. 이 보류는 취소를 따르지 않고 뒤늦게 끝나는 의존성을 의도적으로 모사한다.

워커들은 같은 Node 프로세스에서 SDK client를 공유한다. 다중 호스트의 시계 오차, 운영 lease 5분으로 실행하는 장시간 부하, DB 재시작은 별도다. 다음은 시험 시간·동시 파일 수·처리량·복구 시간 기준을 명시한 부하 시험으로 확장하는 것이다.
