# 여러 청크의 반복 부하와 자원 측정

2026-09-05. `npm run test:network-load-extended`를 추가했다. 기존 작은 문서 시험은 `npm run test:network-load`로 유지한다.

## 조건

워커 3개·파일 12개, 파일당 42,769바이트의 합성 텍스트를 재인덱싱한다. 파일당 16개, 배치당 192개 청크다. 정상·DB 단절을 번갈아 각각 3회 실행한다. 시나리오마다 파일과 연결 풀을 새로 준비하고 기존 인덱스 생성 후 측정을 시작한다. 테스트 프로세스와 PostgreSQL 서버는 실행 간 재시작하지 않는다.

합성 embedding 응답 지연 50ms, 동시 embedding은 파일당 1개, 테스트 lease 1.2초다. 워커 DB 경로 단절 시 기존 전체 인덱스가 유지되는지 검사하고, 복구 후 파일별 청크 번호·내용·1024차원 벡터·새 provenance와 중복 없음을 확인한다. 정상 또는 연결 복구 후 완료 상한은 로컬 회귀용 30초다.

## 자원 지표의 의미

- CPU: `process.cpuUsage()`의 user/system CPU 시간 차이. 재인덱싱 측정 구간 전체를 기준으로 한 코어 대비 평균 사용률을 계산한다. DB 단절 대기 시간도 포함한다.
- 메모리: 같은 Node 프로세스의 RSS·heapUsed 시작/종료 값과 100ms 표본 최댓값. SDK·합성 HTTP 서버·Jest·이미 적재한 초기 인덱스 snapshot도 포함한다.
- DB 연결: 별도 관측용 직접 연결에서 격리 DB의 `pg_stat_activity`를 조회한다. `application_name=network-e2e-worker`인 연결만 집계해 워커의 총 연결·active 연결 표본 최댓값을 기록한다. 관측 연결은 제외한다.
- 표본 조회는 중첩 실행하지 않는다. 조회 실패는 시험 실패로 처리하고, 측정 종료 시 타이머와 진행 중 조회를 정리한다. 최종 무결성 비교는 자원 측정 이후 수행한다.

CPU·메모리는 PostgreSQL 서버나 전체 호스트 지표가 아니다. 100ms 사이의 짧은 사용량 급증은 놓칠 수 있다. RSS 증가만으로 메모리 누수를 판정하지 않으며 강제 GC도 실행하지 않는다.

## 범위와 후속

단일 프로세스·합성 외부 의존성·짧은 lease를 사용하는 제한된 반복 시험이다. 문서 구조는 텍스트 한 종류이며 PDF/Excel 파싱 부하나 AWS quota·비용은 포함하지 않는다. 이전 작은 문서는 파일당 청크 1개였으므로 파일/초만 비교하지 말고 파일 수와 청크 수를 함께 본다.

다음은 여러 프로세스로 워커를 분리하고 실제 운영 lease와 지속 시간을 적용하는 시험이다. 운영 성능 판정에는 독립적인 CPU·메모리·DB 지표와 처리량·복구 SLO를 추가해야 한다.
