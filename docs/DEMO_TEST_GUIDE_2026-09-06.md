## 2. 권장 실행 순서

1. 서비스 홈의 `AI Server 준비됨`, 연결 진단 `READY`를 확인한다. 실패하면 correlation ID를 기록하고 기능 테스트를 중단해 연결부터 확인한다.
2. 검증 데모에 로그인해 `연결 설정` → `STORE_A / STORE_B 검증 환경`이 준비됐는지 확인한다. 이번 실행 시 준비 상태였다.
3. 준비 상태라면 기존 연결과 키를 유지한다. 미준비 상태일 때만 `검증 환경 구성`을 실행한다. 이 동작은 전용 검증 fixture와 키를 구성하므로 반복 실행 전 상태를 확인한다.
4. 아래 자동 계약·경계 검사, 테넌트/지식 검사, Smoke 순서로 실행한다. 각 작업 완료 후 다음 작업을 시작한다.
5. 서비스 고객 질문을 비교하고 테스트 문서를 업로드한다. 답변 반영과 다른 매장 격리를 확인한 뒤 이번 테스트 문서만 보관한다.
6. 결과 JSON, 실패 항목, 요청 ID를 저장한다. 기본 정책/상품 문서는 유지한다. 다음 테스트를 위해 `검증 데이터 정리`는 이번에는 실행하지 않았다.

## 3. 검증 데모: 화면별 절차와 실제 결과

### 자동 계약 검증 탭

`자동 계약 검증`을 선택하고 아래 버튼을 순서대로 실행한다.

| 버튼 | 확인 목적 | 이번 결과 |
|---|---|---|
| 전체 실행 | health/readiness, 인증, 요청 검증, correlation ID, 검색·답변 계약 | 14/14 PASS |
| 노출 정책 검증 | Swagger 노출 정책과 허용되지 않은 Origin의 CORS 응답 | 4/4 PASS |
| 내부 API 경계 검증 | Legacy 지식 쓰기와 내부 조회 차단, 관리자 대체 경로 | 8/8 PASS |

정상 health는 200, 잘못된 인증은 해당 계약의 401/403, 차단된 legacy 경로는 404처럼 **검사의 기대 상태 코드**로 판정한다. 거절 검사의 4xx는 성공일 수 있다. 인증 키가 없어 Skip이 나온 경우 전체 통과로 처리하지 않는다.

### 연결 설정 탭의 검증 환경 버튼

각 버튼의 결과에서 `total`, `passed`, `failed`, `skipped`와 실패 ID를 기록한다. 일부 검사는 테스트 앱 상태·키·문서를 변경하고 복원하거나 테스트 문서를 보관한다. 실제 고객 앱을 대상으로 임의 변경하지 않는다.

| 버튼 | 확인할 내용 | 이번 결과 | 로컬 보고서 |
|---|---|---|---|
| 테넌트 격리 검증 | 매장 간 파일/검색/답변 근거 격리, 비활성 앱 거절 | 6/8, TEN-007·008 FAIL | `tenant.json` |
| 역할 권한 검증 | 소비자·관리자·지식 운영자 API 경계 | 6/6 PASS | `rbac.json` |
| credential 수명주기 검증 | 키 재발급 및 이전 키 거절 등 | 4/4 PASS | `credentials.json` |
| 다중 형식 parser 검증 | 여러 형식의 fixture 처리 | 6/6 PASS | `parsers.json` |
| 지식 전체 흐름 검증 | 업로드·인덱싱·검색·정책 변경·보관 흐름 | 10/10 PASS | `knowledge-lifecycle.json` |
| 지식 정책 matrix 검증 | 접근 수준과 게시 정책 조합별 검색 허용/차단 | 17/17 PASS | `policy-matrix.json` |
| 비동기 인덱싱 작업 검증 | 작업 생성·상태·중복 요청 등 작업 계약 | 5/5 PASS | `index-jobs.json` |
| 지식 파일 거절 검증 | 지원하지 않는 형식·유효하지 않은 파일 등의 거절 | 7/7 PASS | `file-rejection.json` |

### 전체 기능 탭에서 질문 한 건 직접 재현

1. `전체 기능` → `기능`에서 `knowledge.answers`에 해당하는 지식 답변 기능을 선택한다.
2. 경로 파라미터와 Query는 각각 `{}`로 둔다.
3. 요청 본문에 아래 JSON을 넣고 `API 호출`을 누른다. 읽기 질문에는 `파괴적 요청 실행 확인`이 필요하지 않다.
4. HTTP 상태, `answerable`, `answerStatus`, `answer`, `sources`, correlation ID를 함께 확인한다. 문장의 표현은 달라도 정책 사실과 출처가 일치해야 한다.

```json
{
  "query": "교환과 환불 정책을 알려주세요.",
  "strict": true,
  "includeSources": true,
  "maxTokens": 256,
  "temperature": 0
}
```

자료가 없는 질문에는 `answerable: false`, `answerStatus: "insufficient_evidence"`, `sources: []`가 정상일 수 있다. 출처 없는 사실을 만들어내는 답변을 통과시키지 않는다.

### 성능 검증 탭

1. `성능 검증` → `부하 프리셋`에서 Smoke(`smoke`)를 선택한다.
2. 대상은 `knowledge.answers`, 총 요청 수 **5**, 동시 요청 수 **1**인지 확인한다.
3. 위 JSON을 요청 본문으로 사용하고 `성능 시험 실행`을 누른다.
4. 성공률·상태 코드·p50/p95·429·SDK 재시도·토큰을 확인한다.
5. 화면에서 실행했다면 `현재 실행 JSON 저장`으로 저장한다. 반복 비교는 `현재 결과를 비교 기준으로` 또는 `저장된 실행 JSON 불러오기`를 사용하고 같은 질문·동시성·maxTokens로 실행한다. 다운로드/비교 버튼 자체는 이번 브라우저 테스트 대상에 포함하지 않았다.

## 5. 서비스 데모: 관리자 → 고객 → 보관

**이번 실행의 보관 예외:** 10번에서 `window.confirm`을 사용하는 버튼을 누른 후 인앱 브라우저 제어가 응답하지 않았다. 새 탭에서도 동일하여 UI 보관 완료는 **BLOCKED/미검증**으로 남겼다. 테스트 잔여물을 정리하기 위해 관리자 API에서 전용 서비스 STORE_A와 정확한 파일명으로 단 1건을 식별한 뒤 `DELETE /admin/v1/knowledge/apps/{appId}/files/{fileId}`를 호출했다. `deleteObject`는 지정하지 않았으며 결과 `status: archived`를 확인했다. 파일 ID는 `a7d98b90-b314-4c8c-b077-d7638b2c2168`. 브라우저 제어 문제와 서버 보관 API 성공은 구분한다.

새 버전 교체는 새 파일 업로드 → 검색 가능 → 고객 답변 확인 → 이전 버전 보관 순서로 진행한다. 이번 서비스 UI 실행은 한 파일의 업로드·재인덱싱·격리·보관 후 제외를 다뤘으며, 두 버전 동시 게시 전환이나 실제 장애 주입/재시도 UI는 별도로 실행하지 않았다.

## 6. 상담원 검토함

홈 → `고객 상담` → `검토함 열기`를 클릭한다. 허용 계정에서 상담원 전용 접근 확인 화면을 확인했다. 화면은 **영구 검토 요청 저장과 답변·피드백 처리를 다음 S2 작업에서 연결**한다고 명시한다.

따라서 고객 화면의 검토 접수번호가 실제 상담원 영구 대기열에 전달되는 전체 흐름은 현재 완료 기능이 아니다. 테스트 성공 기준은 접근 경계와 현재 세션 내 접수 안내까지이며, 실제 상담 업무 이관 완료로 보고하지 않는다.

## 8. 같은 검사를 명령으로 실행

저장소 루트에서 Node.js로 실행한다. 인증 파일은 `URL:`, `Username:`, `Password:` 필드를 가진 기존 로컬 파일을 사용한다. 키를 명령 인자나 보고서에 넣지 않는다.

```powershell
Set-Location C:\Work\HJSolution\HJ_AI_Server
node scripts/run-demo-acceptance.mjs --execute
```

명시적인 결과 경로가 필요하면 새 경로를 지정한다. 기존 실행 증거를 덮어쓰지 않는다.

```powershell
node scripts/run-demo-acceptance.mjs --execute --output-dir outputs/demo-acceptance/my-next-run
```

실행기는 준비되지 않은 검증 환경에서는 중단한다. `--execute`는 전용 데모 fixture 변경 및 실제 AWS 소규모 호출을 수행한다는 명시 옵션이다. 성공 종료 코드는 0, 실패 또는 Skip 포함은 1이다. 이번 실행은 TEN-007/008 때문에 **종료 코드 1**이었다. 12개 suite 중 11개 통과이며 기능 검사 89건과 성능 요청 5건을 별도로 집계한다.

이번 증거 위치: `outputs/demo-acceptance/2026-09-06-guide/`. `summary.json`과 12개 원본 보고서, 테넌트 추가 진단 결과를 보관했다. Docker 이미지에 Git 메타데이터가 없어 보고서의 `serverCommit`은 `unknown`; 실행 릴리스는 배포 기록의 `20260906-01`로 식별한다.

오류가 나면 실행 시간(KST), 데모 종류, STORE ID, 질문/파일명, 기대값, 실제 HTTP 상태/오류 코드, correlation ID를 함께 남긴다. 401/403은 인증/허용 역할, 404는 경로/차단 정책, 429는 부하/쿼터, 인덱싱 실패는 파일 형식과 작업 상태부터 확인한다. 무조건 키 재발급이나 재업로드를 반복하지 않는다.
