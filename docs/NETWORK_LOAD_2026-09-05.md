# 동시 파일 처리와 DB 복구 시간 측정

2026-09-05. `npm run test:network-load`로 실행하는 별도 부하 회귀 시험을 추가했다. 운영 코드는 변경하지 않았다.

## 조건과 판정 기준

- 시나리오마다 24개 파일을 먼저 인덱싱한 뒤 동일 파일의 재인덱싱 24개를 대기열에 넣는다. 초기 인덱싱·파일 생성·작업 제출 시간은 측정에서 제외한다.
- 워커 1개/3개와 정상/DB 단절의 네 가지 조합을 각각 한 번 실행한다. 워커별 DB pool은 독립적이고 최대 연결은 2개다. 단일 Node 프로세스에서 SDK client를 공유한다.
- 실제 격리 PostgreSQL 및 HTTP/1 S3·HTTP/2 embedding 합성 응답을 사용한다. 파일당 청크 1개, 1024차원 벡터, 합성 embedding 응답 지연은 50ms다. 실제 AWS 호출은 없다.
- 단절은 첫 embedding 요청에서 워커 DB 경로를 차단하고 테스트 lease 1.2초의 3배 이상 유지한다. 단절 중 기존 청크 전체가 보존되고 작업 상태가 processing/attempt 1 또는 queued/attempt 0인지 검사한다.
- 복구 후 24개 모두 완료, 파일별 청크 정확히 1개, 기대 내용·벡터·새 provenance, 중단된 작업만 attempt 2, 추가 drain 시 변경·추가 호출 없음을 검사한다.
- 정상 전체 완료 또는 연결 복구 후 전체 완료가 15초 미만이어야 한다. 이는 로컬 회귀 실패를 잡는 여유 있는 상한이며 운영 SLO가 아니다.

## 범위와 후속

회귀 확인: `npm run verify`의 build/typecheck/lint·서버 197개·데모 37개 PASS. `npm run test:queue-http-e2e`는 7 suites / 39개 PASS, 전용 부하 4개 skip, 43.859초. 통합 임시 DB `queue_e2e_2c6aa97b59b14cdba39882f86480a3a0`도 삭제 완료.

기본 통합 회귀에서는 부하 4개를 건너뛰며 전용 명령에서만 실행한다. 단일 실행·작은 동일 구조 문서·고정 합성 지연의 비교 결과로 최대 처리량이나 운영 capacity를 추정하지 않는다. CPU·메모리·DB 연결 사용량과 장시간 안정성은 아직 측정하지 않았다.

다음은 문서 크기와 청크 수를 늘린 반복 시험에 자원 사용량을 함께 기록하고, 실제 운영 lease와 시험 시간·비용·SLO를 정한 장시간 부하 검증으로 확장하는 것이다.
